# รายงานการพัฒนาและทดสอบเว็บ IoT Dashboard ด้วย ThingsBoard

**รายวิชา:** CPE 23367 ระบบสมองกลฝังตัว  
**รหัสนักศึกษา:** 68069710  
**วันที่จัดทำ:** 19 ตุลาคม 2569  
**อุปกรณ์:** ESP32-S3, MPU-6050 และ LED จำลองด้วย Wokwi  
**แพลตฟอร์ม:** thingsboard.cloud  
**สถานะรายงาน:** สรุปจากโค้ด ผลทดสอบจำลอง และผลใช้งานจริงที่ผู้ทดสอบยืนยัน ยังต้องแนบภาพและตรวจรายการคงเหลือก่อนส่งฉบับสมบูรณ์

## 1. วัตถุประสงค์

1. สร้างหน้า Login และ Dashboard ด้วย HTML, CSS และ JavaScript โดยใช้ native browser APIs
2. เชื่อมต่อ ThingsBoard REST API สำหรับยืนยันตัวตนและสั่งงาน LED
3. รับข้อมูลเซนเซอร์ผ่าน WebSocket และแสดงค่าบนเว็บแบบเรียลไทม์
4. ใช้กระบวนการ AI Loop Engineering วางแผน สร้าง ตรวจ แก้ไข และบันทึกผล
5. ประเมินข้อผิดพลาดด้าน UI การทำงาน API และการจัดการข้อมูลยืนยันตัวตน พร้อมจัดทำหลักฐาน Before/After

## 2. โครงสร้างและการทำงาน

```text
MPU-6050 → ESP32-S3 ใน Wokwi → MQTT → ThingsBoard
                                         ↓ WebSocket
                                   เว็บ Dashboard
                                         ↓ REST RPC
ThingsBoard → MQTT → ESP32-S3 → เปิด/ปิด LED
```

เฟิร์มแวร์อ่านอุณหภูมิ ความเร่งสามแกน ความเร็วเชิงมุมสามแกน และมุมสามแกน ส่งขึ้น ThingsBoard ทุกประมาณ 1 วินาที เว็บใช้บัญชี Customer User เข้าสู่ระบบ ตรวจข้อมูลบัญชี เลือกอุปกรณ์ตัวแรกของ Customer และอ่าน credentials ก่อนเปิด Dashboard

เว็บประกอบด้วยกราฟความเร่ง X/Y/Z ในช่วงเวลา 8 วินาที ช่องแสดงค่าเซนเซอร์ 10 ค่า ตัวแสดงการเอียงที่แมป acc_x และ acc_y ช่วง −1 ถึง +1 g และสวิตช์ LED ใช้คำสั่ง two-way RPC เพื่อรออุปกรณ์ยืนยัน

## 4. ขั้นตอนดำเนินงาน

1. ตรวจโปรเจกต์ ใส่ Device Access Token ในเฟิร์มแวร์ และตั้ง `STUDENT_ID` เป็น `68069710` โดยไม่เผยแพร่ค่า Token ในรายงาน
2. อ่านเอกสารโจทย์และไฟล์ข้อกำหนด กำหนดใช้ Customer User ตามโจทย์ แม้ผู้ใช้มีบัญชี Tenant Admin ด้วย
3. จัดทำแผนงานและพัฒนาหน้า Login พร้อมตรวจข้อมูลและแสดงสถานะระหว่างเชื่อมต่อ
4. สร้างลำดับ Login → ข้อมูลบัญชี → รายการอุปกรณ์ → credentials → Dashboard
5. ทดสอบ API ด้วยข้อมูลจำลอง และตรวจรูปแบบคำขอเทียบ API contract
6. ตรวจปัญหา 403 ที่เกิดกับบัญชีจริง ปรับข้อความให้ระบุขั้นตอนที่ถูกปฏิเสธ และเพิ่มเวอร์ชันไฟล์เพื่อโหลดโค้ดล่าสุด
7. ผู้ใช้ตรวจและปรับการตั้งค่าบัญชีใน ThingsBoard แล้วเข้าสู่ Dashboard สำเร็จ ไม่มีหลักฐานในบทสนทนาที่ระบุค่าตั้งสิทธิ์สุดท้ายทั้งหมด
8. เพิ่มกราฟ ค่าเซนเซอร์ Tilt และ LED พร้อมการแจ้งข้อมูลเก่าและการจัดการสตรีมหลุด
9. ผู้ใช้ทดสอบกับ Wokwi และยืนยันผล Login, LED, ข้อมูลสด, Logout และกรณีอุปกรณ์หยุดทำงาน

| ปัญหา | อาการ Before | การดำเนินการ | ผล After / ข้อจำกัด |

## 6. ผลการทดสอบ

### 6.1 การใช้งานจริงที่ผู้ทดสอบยืนยัน

| กรณี | วิธีทดสอบ | ผลที่ได้รับ |
| --- | --- | --- |
| Login | เข้าด้วย Customer User | ผ่าน: เข้าหน้า Dashboard และเห็น Device ID |
| LED | สั่งเปิดและปิดจากเว็บขณะ Wokwi ทำงาน | ผ่าน: LED ใน Wokwi เปลี่ยนตาม |
| ข้อมูลสด | เปลี่ยนค่า MPU-6050 ใน Wokwi | ผ่าน: หน้าเว็บเปลี่ยนตาม ผู้ใช้ไม่ได้แยกยืนยันรายละเอียดทุก widget |
| Logout | กด Logout | ผ่านตามคำยืนยันผู้ใช้ ยังไม่ได้ตรวจ storage cleanup แยก |
| อุปกรณ์หยุดทำงาน | หยุด Wokwi แล้วส่งคำสั่ง LED | ผ่าน: เว็บแจ้งไม่ตอบสนอง |

### 6.2 การทดสอบจำลอง API

หลักฐาน: [auth-tests.json](DemoApp/evidence/auth-tests.json) และ [ชุดทดสอบ](DemoApp/tests/auth.test.mjs) รวม **14 กรณีผ่าน** ได้แก่:

1. Customer login ครบลำดับและล้าง session
2. Login 401: แสดงข้อผิดพลาด ไม่ retry และล้าง session
3. Login 404: แสดงข้อผิดพลาด ไม่ retry และล้าง session
4. Login 503: แสดงข้อผิดพลาด ไม่ retry และล้าง session
5. 403 ขณะอ่านข้อมูลบัญชี: ระบุขั้นตอนถูกต้อง
6. 403 ขณะอ่านรายการอุปกรณ์: ระบุขั้นตอนถูกต้อง
7. 403 ขณะอ่าน credentials: ระบุขั้นตอนถูกต้อง
8. JSON ตอบกลับผิดรูปแบบ: จัดการเป็นข้อความผิดพลาด
9. ใช้ Tenant Admin: ปฏิเสธตามข้อกำหนด Customer User
10. ไม่มีอุปกรณ์: แสดงข้อความและล้าง session
11. Protected API ได้ 401: refresh แล้ว retry หนึ่งครั้ง
12. Refresh ล้มเหลว: ไม่ retry ซ้ำและล้าง session
13. เครือข่ายขัดข้อง: จัดการข้อผิดพลาดโดยไม่ retry
14. AbortError: แสดงข้อความหมดเวลา การทดสอบนี้จำลองการ abort ไม่ได้จับเวลารอจริงครบ 10 วินาที

### 6.3 การตรวจโค้ดและข้อมูลเซนเซอร์

- `node --check` ผ่านสำหรับไฟล์ JavaScript ที่พัฒนา
- ตรวจค่าที่ไม่ถูกต้อง เช่น null, ข้อความว่าง, NaN, ค่าเกินช่วง และ key ที่ไม่รู้จัก: ผ่านในการทดสอบโมเดลข้อมูล
- ตรวจการแมปและ clamp ของ Tilt: ผ่านในการทดสอบฟังก์ชัน
- ตรวจช่วงเวลา 8 วินาทีที่ 20 Hz: ผ่าน โดยมี 161 จุดเมื่อรวมขอบเวลาเริ่มและสิ้นสุด
- ตรวจ timestamp อนาคตเกินเกณฑ์: ผ่านในการทดสอบฟังก์ชัน
- การตรวจเหล่านี้ไม่ทดแทนการตรวจภาพกราฟหรือความลื่นไหลใน browser จริง

## 7. การตรวจ API และข้อมูลยืนยันตัวตน

เว็บไม่มี custom backend ของตนเอง ใช้ ThingsBoard เป็น backend การตรวจ backend integration จึงเน้นวิธีเรียก REST/WebSocket และการจัดการผลตอบกลับ

| รายการ | สิ่งที่ตรวจพบในโค้ด/ผลทดสอบ | ขอบเขตการยืนยัน |
| --- | --- | --- |
| Token storage | เก็บ JWT, refresh token และ device credentials ใน sessionStorage | ตรวจจากโค้ดและ mock tests |
| รหัสผ่าน | ไม่บันทึกรหัสผ่านลง storage | ตรวจจากโค้ดและ mock tests |
| Console | ไม่พบ console calls ใน `DemoApp/js/` | เป็น source scan ยังไม่ได้ตรวจ runtime console และไม่ได้ครอบคลุมไฟล์เดิมทุกโฟลเดอร์ |
| DOM | ไม่พบ innerHTML ใน JS ใหม่ ใช้ textContent/DOM APIs | ตรวจเฉพาะโค้ดเว็บที่พัฒนา |
| Status codes | 401/403/404/503 มีข้อความที่อ่านเข้าใจได้ | ผลจำลอง; 403 มีหลักฐานใช้งานจริงด้วย |
| Token refresh | Protected 401 refresh/retry ครั้งเดียว | ผลจำลอง; concurrent refresh ยังไม่ได้ทดสอบแยก |
| Request deadline | มี AbortController ระยะ 10 วินาที | ตรวจโค้ดและจำลอง AbortError |
| WebSocket | มี backoff 1, 2, 4, 8, 16, 30 วินาทีและ cleanup | ตรวจโค้ด ยังไม่ได้จับเวลาทดสอบจริง |

รายงานนี้ไม่ใส่ Access Token, JWT หรือรหัสผ่าน และไม่อ้างว่าได้ตรวจความปลอดภัยทั้ง repository แล้ว

## 8. หลักฐาน Before/After ที่ต้องแนบ

ภาพจากบทสนทนาบางภาพยังไม่ได้ถูกบันทึกลงโฟลเดอร์โปรเจกต์ จึงเว้นตำแหน่งภาพไว้โดยไม่สร้างภาพผลทดสอบขึ้นใหม่

| หมายเลข | ภาพที่ควรแนบ | คำอธิบายใต้ภาพ |
| --- | --- | --- |
| 1 | Login Before: error สิทธิ์แบบทั่วไป | ก่อนปรับข้อความ ไม่ทราบขั้นตอนที่ถูกปฏิเสธ |
| 2 | Login After: error ระบุการอ่านรายการอุปกรณ์ | หลังปรับข้อความ ระบุการอ่านรายการอุปกรณ์ได้ชัดเจน |
| 3 | Dashboard Before: Login checkpoint | โครงหน้า Dashboard หลัง Login สำเร็จ ก่อนเพิ่ม widgets |
| 4 | Dashboard After: ข้อมูลสดและกราฟ | หน้า Dashboard หลังเพิ่มกราฟ ค่าเซนเซอร์ Tilt และ LED |
| 5 | เว็บพร้อม LED ใน Wokwi | หลักฐานคำสั่งเปิด/ปิดจากเว็บทำงานจริง |
| 6 | ข้อความอุปกรณ์ไม่ตอบสนอง | หยุด Wokwi แล้วสั่ง LED เว็บแสดงข้อผิดพลาด |

> ใส่ภาพ 1–6 ในส่วนนี้หรือแนบท้ายรายงาน พร้อมปิดบังข้อมูลส่วนตัวและข้อมูลยืนยันตัวตนก่อนส่ง

## 9. ลำดับ Prompt สำหรับทำงานทีละขั้น

```text
ตรวจฟอร์มว่างและการใช้คีย์บอร์ด แล้วรายงานผลที่ตรวจได้จริง
```

### ขั้นที่ 4: เชื่อมต่อ REST และจัดการเซสชัน

```text
สร้าง auth.js และ login.js ตาม API contract:
Login → Get Current User → Customer Devices → Device Credentials → Dashboard
เก็บ Token เฉพาะ sessionStorage ไม่เก็บรหัสผ่านและไม่พิมพ์ credentials ลง console
ตั้ง deadline 10 วินาที ตรวจ status/JSON และข้อมูลสำคัญก่อนใช้
Protected API ได้ 401 ให้ refresh และ retry อย่างละหนึ่งครั้ง
ถ้า login/refresh ล้มเหลวไม่ retry อัตโนมัติ และล้างเซสชันเมื่อ login chain ล้มเหลว
สร้าง Dashboard shell เพื่อทดสอบ Login และ Logout ก่อนหยุดที่ checkpoint
```

### ขั้นที่ 5: วิเคราะห์และแก้ปัญหา 403

```text
Login พบ 403 ให้ตรวจว่าติด API ขั้นตอนไหน
แยกข้อความผิดพลาดสำหรับข้อมูลบัญชี รายการอุปกรณ์ และ Device Credentials
แนะนำให้ Tenant Admin ตรวจ Customer, กลุ่มผู้ใช้ และสิทธิ์อ่านตามจุดที่ติด
ห้ามใช้บัญชี Admin หรือ hard-code token เพื่อข้ามสิทธิ์
เพิ่ม regression tests และหากยังโหลดข้อความเก่าให้ตรวจไฟล์ที่เสิร์ฟและ cache version
```

### ขั้นที่ 6: สร้าง Dashboard

```text
เพิ่มกราฟ canvas ความเร่ง X/Y/Z แบบ rolling window 8 วินาที รองรับ 1–20Hz
เพิ่มค่า acc_x/y/z, gyro_x/y/z, angle_x/y/z และ mpu_temp พร้อมหน่วยตาม contract
เพิ่ม Tilt 2D จาก acc_x/acc_y แมป −1 ถึง +1 g เป็น 0–100% และ clamp ขอบ
ตรวจค่าผิดรูปแบบ ค่าเกินช่วง timestamp และละเว้น key ที่ไม่ใช้
ข้อมูลเก่าให้แจ้งผู้ใช้และไม่สร้างข้อมูลจำลองปนในหน้าจอจริง
```

### ขั้นที่ 7: เชื่อม WebSocket และ LED

```text
สมัคร telemetry และ led_state ผ่าน WebSocket ตาม contract
เชื่อมต่อใหม่ด้วย backoff 1,2,4,8,16,30 วินาที มี deadline และ cleanup
อ่านสถานะ LED เริ่มต้นจาก CLIENT_SCOPE และอัปเดตจาก attribute subscription
สั่ง LED ด้วย two-way RPC method setLed และ params เป็น boolean
ระหว่างรอคำตอบให้ปิดปุ่มชั่วคราวและไม่รับ attribute มาทับคำสั่ง
สำเร็จใช้สถานะจากอุปกรณ์ ล้มเหลวคงสถานะเดิมและแสดงข้อความ
Logout ต้องปิดสตรีม ยกเลิก timers และล้างข้อมูลเซสชัน
```

### ขั้นที่ 8: ทดสอบกับ Wokwi และบันทึกผล

```text
ทดสอบ Login ด้วย Customer User, เปิด/ปิด LED และปรับค่า MPU-6050 ใน Wokwi
ตรวจว่าเว็บเปลี่ยนตาม จากนั้นทดสอบ Logout
หยุด Wokwi แล้วส่งคำสั่ง LED ตรวจข้อความไม่ตอบสนองและการคืนสถานะสวิตช์
บันทึกเฉพาะสิ่งที่ผู้ทดสอบเห็นจริงใน CLARIFICATIONS.md และ SESSION.md
อย่าทำเครื่องหมายผ่านให้รายละเอียดที่ยังไม่ได้ยืนยัน
```

### ขั้นที่ 9: ตรวจและเก็บหลักฐานที่ยังเหลือ

```text
ตรวจ UI ที่ 320/768/1280px พร้อม keyboard focus และ horizontal overflow
ทดสอบ reconnect, failed-command rollback และ session cleanup แยกให้ชัดเจน
ตรวจ browser console โดยไม่เผย Token และทดสอบ API error cases ด้วย mocks
เก็บภาพ Login และ Dashboard แบบ Before/After จากผลจริง
หากไม่มี browser หรือหลักฐาน ให้ระบุว่ายังไม่ได้ตรวจ ห้ามสร้างผลผ่านหรือภาพผลทดสอบขึ้นเอง
```

### ขั้นที่ 10: จัดทำรายงานและทบทวนขั้นสุดท้าย

```text
จัดทำรายงานภาษาไทยสำหรับรหัสนักศึกษา 68069710
ระบุวัตถุประสงค์ สถาปัตยกรรม ไฟล์ ขั้นตอน ปัญหา สาเหตุ วิธีแก้ และผลทดสอบ
แยกผลจริง ผล mock ผลตรวจ source และรายการที่ยังไม่ได้ตรวจ
แนบ Before/After พร้อม prompt และระบุว่าข้อความใดเป็น prompt เรียบเรียงย้อนหลัง
ไม่ใส่รหัสผ่านหรือ Token ตรวจทุก requirement และรอ human review ก่อนประกาศเสร็จสมบูรณ์
```

## 11. สรุปผล

ระบบเชื่อมข้อมูลจากอุปกรณ์จำลองผ่าน ThingsBoard มายังเว็บได้ และผู้ทดสอบยืนยันการควบคุม LED รวมถึงการแจ้งข้อผิดพลาดเมื่ออุปกรณ์หยุดทำงาน ปัญหาที่พบระหว่างพัฒนาคือสิทธิ์ของ Customer User ข้อความผิดพลาดที่ไม่เจาะจง และการโหลดข้อความจากไฟล์เวอร์ชันเดิม การตรวจและปรับระบบช่วยให้ระบุปัญหาและทดสอบเส้นทางใช้งานหลักได้ ส่วนภาพประกอบและการตรวจรายละเอียดที่ระบุว่ายังค้างต้องทำต่อก่อนถือเป็นงานส่งฉบับสมบูรณ์
